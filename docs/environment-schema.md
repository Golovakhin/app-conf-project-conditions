# Схема окружения CarRentSGM

**Команда:** Кондиции
**Проект:** CarRentSGM — приложение для управления арендой автомобилей.
**Дата актуализации:** 2026-10-14

**Статус:** схема реализована в `compose.yaml` и проверена командой на этапе 5 практики №3.
Чистый запуск после `docker compose down -v` выполнен успешно командой
`docker compose up --build`. База получила статус `healthy`, а `/health`
вернул `200` и `{"status":"healthy","database":"ok"}`.

## 0. Кто что делал

Известно, что сокомандник выполнил этапы 1–3 практики №3, а Монахов Георгий приступил к этапу 4.
Имена исполнителей этапов 1–3 и распределение ролей именно на воркшопе команда должна уточнить.
Автор ADR 002 и внешний рецензент пока не зафиксированы; участие отсутствующих участников не предполагается.

## 1. Схема

```text
Браузер / curl на ноутбуке
          |
          | localhost:${APP_PORT:-8000} → порт 8000 контейнера
          v
app: FastAPI + Uvicorn, Python 3.12, зависимости через uv
          |
          | DATABASE_URL → db:5432, база app
          v
 db: PostgreSQL 16
          |
          | /var/lib/postgresql/data
          v
 pgdata: именованный том Docker
```

Оба сервиса находятся в общей сети Compose. Приложение обращается к базе
по имени сервиса `db`, а не по `localhost`. Сервис `app` запускается после
успешного healthcheck сервиса `db` (`condition: service_healthy`).

## 2. Таблица сервисов

| Сервис | Образ или сборка | Порты `хост:контейнер` | Переменные окружения (только имена) | Тома | Зависит от (условие) | Healthcheck |
|---|---|---|---|---|---|---|
| `app` | Сборка из `Dockerfile`, контекст `.`; база `python:3.12-slim`; uv из `ghcr.io/astral-sh/uv:0.13.1` | `${APP_PORT:-8000}:8000` — доступ браузера и curl к API | `DATABASE_URL` | Нет | `db`, `condition: service_healthy` | Проверка вручную: `GET /health`; отдельный healthcheck контейнера на этом этапе не задан |
| `db` | `postgres:16` | На хост не публикуется; внутри сети Compose — `5432` | `POSTGRES_PASSWORD`, `POSTGRES_DB` | `pgdata:/var/lib/postgresql/data` | Нет | `pg_isready -h localhost -U postgres -d app`; interval `5s`, timeout `3s`, retries `10`, start_period `30s` |

Дополнительные сервисы сейчас не нужны: для проверки подключения FastAPI
к PostgreSQL достаточно приложения и базы.

Имя базы — `app`, пользователь — стандартный `postgres`.
Пароль хранится только в локальном `.env`. Compose получает его через
`${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}` и формирует `DATABASE_URL`
для приложения. В Git хранится `.env.example` без настоящего пароля.
`APP_PORT` используется Compose для настройки порта хоста; передавать его
в контейнер приложения не требуется. Порт PostgreSQL наружу не публикуется,
поскольку приложение подключается к нему внутри сети Compose.

Менеджер зависимостей — **uv**. Прямые зависимости проекта:
`fastapi`, `uvicorn[standard]`, `psycopg[binary]`.
`pyproject.toml` допускает Python от 3.11, а `.python-version` и Dockerfile
выбирают Python 3.12. Версии пакетов фиксирует `uv.lock`.

## 3. Ответы на контрольные вопросы

### 1. Адрес базы

Шаблон строки подключения без пароля:

```text
postgresql://postgres@db:5432/app
```

Полную строку с паролем приложение получает в переменной `DATABASE_URL`.
Внутри контейнера `localhost` означал бы сам контейнер приложения,
поэтому для базы используется имя сервиса `db`.

### 2. Судьба данных

`docker compose down` удаляет контейнеры и сеть проекта, но сохраняет
именованный том `pgdata`. При следующем запуске база использует прежние данные.

`docker compose down -v` удаляет также том с данными базы. Следующий запуск
инициализирует новую пустую базу. Эту команду используем для проверки
чистого старта только с учебными данными, которые можно удалить.

### 3. Образ и запуск

При сборке Dockerfile сначала копирует `pyproject.toml` и `uv.lock`, затем
выполняет `uv sync --locked --no-dev --no-install-project`. Зависимости
устанавливаются в `/app/.venv`. После этого `COPY . .` копирует исходный код
и остальные файлы, не исключённые через `.dockerignore`.

Локальные `.venv`, `venv`, `env`, `.git`, `.env`, кэши Python и настройки IDE
исключены из контекста сборки. Окружение `/app/.venv` создаётся внутри образа.
Изменение только кода позволяет повторно использовать слой зависимостей.

При запуске передаются `DATABASE_URL` приложению, `POSTGRES_PASSWORD`
и `POSTGRES_DB` базе, подключаются том и сеть, публикуется порт приложения.
Секреты в образ не встраиваются.

Команда приложения из Dockerfile:

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

### 4. Миграции

На практике №3 официальный образ PostgreSQL при первом запуске с пустым
томом создаёт базу `app`. Таблицы предметной области пока не создаются:
`GET /health` выполняет `SELECT 1`, которому таблицы не нужны.

**Гипотеза для модуля 3:** структуру таблиц будем создавать и обновлять
миграциями Alembic перед запуском приложения. Инструмент и порядок запуска
миграций ещё не реализованы и должны быть проверены отдельно.

### 5. Запуск и проверка

Перед первым запуском скопировать `.env.example` в `.env`
и задать локальный пароль `POSTGRES_PASSWORD`.
`APP_PORT` по умолчанию равен `8000`; при занятом порте выбрать другой.

Поднять весь стек из корня проекта:

```bash
docker compose up --build
```

В другом терминале проверить:

```bash
docker compose ps
curl -i http://localhost:8000/health
```

Если `APP_PORT` изменён, в URL подставить выбранный порт.
В PowerShell использовать `curl.exe` вместо `curl`.
Ожидается: контейнер базы имеет статус `healthy`, приложение отвечает
`200 OK` и `{"status":"healthy","database":"ok"}`.
При недоступной базе `/health` возвращает `503`, а `GET /` продолжает отвечать `200`.
До подключения `DATABASE_URL` ответ `/health` — `503` с указанием,
что переменная не задана.

**Результаты проверки командой 2026-10-14:**

- `docker compose up --build -d`: приложение работает, база имеет статус `healthy`;
  `/health` возвращает `200` и `{"status":"healthy","database":"ok"}`.
- После `docker compose stop db`: `/health` возвращает `503`, а `GET /` — `200`.
- После `docker compose start db`: `/health` снова возвращает `200`
  без перезапуска контейнера приложения.
- Чистый запуск: после `docker compose down -v` команда
  `docker compose up --build` подняла стек с первой попытки,
  `/health` вернул `200`. После проверки стек остановлен через `Ctrl+C`.

**Вопросы авторам** задавайте, только когда схема не отвечает сама. Если ответ автора в схеме не записан — это замечание, даже если ответ правильный: на практике №3 по схеме будут писать compose-файл, а не по устным пояснениям.

**Замечание строится по формуле:** где → что не так → чем это грозит → что предлагаете.

| Не замечание                               | Замечание                                                                                                                                                                  |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| «Всё хорошо» — без указания, где проверяли | «Раздел 2, строка `db`: образ `postgres` без тега. Завтра скачается другая версия, и путь тома может не подойти. Предлагаем `postgres:16`»                                 |
| «Непонятно с базой»                        | «Вопрос 1: приложение подключается к `localhost:5432`. Внутри Compose это сам контейнер приложения, база не найдётся. Предлагаем хост `db` — имя сервиса из вашей таблицы» |
| «Надо доработать порты»                    | «Раздел 2, строка `db`: порт `5432:5432` открыт наружу, зачем — не сказано. Если снаружи к базе никто не ходит, предлагаем убрать»                                         |

**Схема без замечаний — нормальный результат,** если он доказан: у каждого ✅ в комментарии указано, где в схеме вы это увидели. Выдуманное замечание хуже честного «замечаний нет»: авторы потратят время на проблему, которой нет.

**Замечание и рекомендация — разные вещи.** Замечание — схема нарушает критерий, стек не поднимется. Рекомендация или вопрос — то, что схема не обязана решать сейчас, но стоит обдумать. Например: «что будет, если у кого-то занят порт 8000?», «чем окружение на сервере будет отличаться от этого?», «куда приложение будет писать логи?». Рекомендация или вопрос есть в каждом ревью.

Проверяется схема, а не люди. Не переписывайте схему за авторов: ваша задача — показать, где она не сработает.
