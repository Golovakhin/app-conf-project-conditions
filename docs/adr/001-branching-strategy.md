# ADR 001: Выбор стратегии ветвления Git

## Контекст

Наша команда разрабатывает **CarRentSGM** — приложение для управления арендой автомобилей — в рамках курса «Управление конфигурацией бизнес-приложений».

Характеристики проекта:

- **Размер команды:** 3 человека
- **Продолжительность проекта:** 16 недель (1 семестр)
- **Частота релизов:** промежуточные демоверсии каждые 2 недели + финальный релиз в конце семестра
- **Уровень владения Git в команде:** Головахин — уверенно, Монахов — уверенно, Савченко — базовый уровень
- **Требования к стабильности main:** высокие, т. к. проект оценивается преподавателем и другими командами

**Проблема:** Нам нужно выбрать стратегию ветвления Git, которая позволит:

1. Параллельно работать над несколькими фичами без конфликтов
2. Обеспечить стабильность основной ветки
3. Соответствовать требованиям курса DoD (PR с одобрением, чистая история)
4. Быть посильной для нашей команды по уровню сложности

## Рассмотренные варианты

### Вариант А: GitFlow

**Суть:** Строгая стратегия с отдельными ветками `main`, `develop`, `release`, `hotfix` и `feature`.

**Плюсы:**

- Четкое разделение сред (разработка, релиз, продакшн)
- Предсказуемый процесс релизов
- Подходит для больших команд, выпускающих релизы по расписанию

**Минусы:**

- Излишняя сложность для небольшой команды
- Ветка `develop` постоянно отстает от `main`, что приводит к конфликтам
- Требует дисциплины, которую сложно поддерживать в учебном проекте

**Подходит ли нам:** Нет — для команды из трех человек, выпускающей релизы раз в две недели, это перебор.

### Вариант Б: GitHub Flow

**Суть:** Простая стратегия: `main` всегда стабилен, фичи разрабатываются в недолговечных ветках и объединяются через PR.

**Плюсы:**

- Простота и понятность для новичков
- Быстрая интеграция и обратная связь
- Идеально соответствует курсу DoD (PR с одобрением)

**Минусы:**

- Нет интеграционной ветки — нестабильный код может попасть в `main`
- Требует быстрого ревью кода
- Большие фичи могут создавать конфликты

**Подходит ли нам:** Да — простота и соответствие курсу DoD перевешивают минусы, которые можно нивелировать.

### Вариант C: разработка на основе магистральной ветки

**Суть:** Все разработчики коммитят в `main` как можно чаще (минимум раз в день), используя флаги функций для скрытия незавершенных фич.

**Плюсы:**

- Минимум конфликтов при слиянии
- Быстрая обратная связь
- Подходит для практик непрерывного деплоя

**Минусы:**

- Требует высокого уровня CI/CD и автотестов
- Нужна культура feature flags, которой у нас пока нет
- Сложно для новичков в команде

**Подходит ли нам:** Нет — у нас нет мощного CI/CD и опыта работы с feature flags.

## Решение

Мы выбрали стратегию **GitHub Flow**.

### Схема ветвления


Схема ветвления:

```
main ────●────────────────────●────>  (стабильна, готова к демо)
          \                  /
           ●──────●─────────
           feature/version-endpoint
                     │
                     ├── PR создан
                     ├── review (≤ 24 ч, ответ на замечания)
                     ├── approval (мин. 1 от другого участника)
                     └── merge в main → ветка удалена 
```
### Правила работы с ветками

1. Ветка `main` всегда стабильна и готова к демонстрации; изменения в неё попадают только через PR.
2. Каждая фича разрабатывается в отдельной ветке, созданной от актуальной `main`.
3. Имена веток: `<тип>/<краткое-описание>`, где тип — `feature/`, `bugfix/`, `docs/`, `chore/`; описание — латиницей в нижнем регистре, слова через дефис (примеры: `feature/version-endpoint`, `bugfix/health-response`, `docs/pr-template`).
4. Сообщения коммитов соответствуют Conventional Commits: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `merge`. Формат: `<тип>: <описание изменения>`.
5. Перед слиянием в `main` обязателен PR с минимум одним одобрением от другого участника с правом записи; собственный PR участник не одобряет.
6. Конфликты разрешаются в рабочей ветке через `git merge origin/main`; force-push не используется.
7. Ветки удаляются после слияния.

## Обоснование решения

Почему мы выбрали именно эту стратегию?

**Соответствие размеру команды:** Для команды из 3 человек GitHub Flow достаточно прост, чтобы его быстро освоил Савченко (базовый уровень Git). GitFlow создал бы лишнюю бюрократию.

**Частота релизов:** Наши демоверсии выходят каждые 2 недели, что требует частой интеграции. GitHub Flow позволяет мержить фичи по мере готовности, а не ждать релиза.

**Уровень опыта команды:** У нас один человек с базовым уровнем владения Git. GitHub Flow проще для понимания — всего 2 типа веток (`main` и `feature`), без `develop` и `release`.

**Требования курса DoD:** DoD требует, чтобы все изменения попадали в `main` через PR с одобрением. GitHub Flow построен на этой практике, поэтому идеально соответствует требованиям.

## Последствия

### Положительные (+)

- Простота: вся команда быстро освоит процесс
- Быстрая интеграция: фичи мержатся каждые 2–3 дня
- Полное соответствие курсу DoD
- Легко настроить правила защиты веток

### Отрицательные (-)

- Нет интеграционной ветки — для проверки стабильности приходится полагаться на ручную проверку и ревью
- Требует быстрого ревью кода (иначе накапливаются PR)
- Большие фичи могут приводить к конфликтам

## Риски и способы их снижения

| Риск | Вероятность | Влияние | Способ снижения |
|------|-------------|---------|-----------------|
| Конфликты при слиянии больших фич | Средняя | Среднее | Разбиваем большие фичи на мелкие PR и сливаем их каждые 2–3 дня. Регулярно синхронизируем feature-ветку с main через `git merge origin/main` |
| Нестабильный код попадает в `main` | Низкая | Высокая | Правила защиты ветки: обязательный PR и минимум одно одобрение, проверка по чек-листу (11 критериев) |
| Прямой push в `main` в обход PR | Низкая | Высокая | Настраиваем Ruleset / Branch protection на `main`, проводим инструктаж команды |
| PR накапливаются из-за медленного рассмотрения | Средняя | Среднее | Договорились: ревью в течение 24 часов. Если ревьюер занят, просим другого сокомандника |
| Ошибки Савченко из-за базового уровня Git | Средняя | Среднее | Парное программирование с Головахиным/Монаховым на первых PR, помощь при конфликтах |
