\# Правила работы в команде "Кондиции"



\## Git-стратегия



Мы используем Git Flow.



\### Ветвление

\- `main` — стабильная версия

\- `develop` — интеграционная ветка

\- `feature/\[название]` — новые функции

\- `bugfix/\[название]` — исправление багов



\### Коммиты

Используем \[Conventional Commits](https://www.conventionalcommits.org/):

\- `feat:` новая функция

\- `fix:` исправление бага

\- `docs:` изменения в документации

\- `style:` форматирование кода

\- `refactor:` рефакторинг

\- `test:` добавление тестов

\- `chore:` рутинные задачи



Пример: `feat: add user authentication endpoint`



\## Code Review



\- Каждый PR требует минимум 1 approval от другого участника команды

\- Ревьюер проверяет: стиль кода, архитектуру, наличие тестов

\- Автор отвечает на все комментарии в PR



\## Встречи команды



\- Частота: 2 раза в неделю

\- Канал связи: Telegram (ссылка будет добавлена)

\- Время ответа на сообщения: в течение 24 часов



\## Разрешение конфликтов



1\. Обсуждение в команде

2\. Голосование (большинство голосов)

3\. Если не можем решить — обращаемся к преподавателю

# Правила работы в команде «Кондиции»

Проект: CarRentSGM — приложение для управления арендой автомобилей.

## 1. Стратегия ветвления

Используем GitHub Flow.

main ────●────────────────────●────>
          \                  /
           ●──────●─────────
           feature/version-endpoint
                     PR → review → approval

Единственная долгоживущая ветка — main.
Рабочая ветка создаётся от актуальной main.
Готовое изменение возвращается в main через Pull Request
после проверки другим участником.
После объединения рабочая ветка удаляется.

Эта схема и правила должны совпадать с ADR 001:
docs/adr/001-branching-strategy.md.

## 2. Правила именования веток

Формат: <тип>/<краткое-описание>.
Описание пишем латиницей в нижнем регистре, слова разделяем дефисами.

Типы:
- feature/ — новые функции;
- bugfix/ — исправления ошибок;
- docs/ — документация;
- chore/ — настройки и зависимости.

Примеры:
- feature/version-endpoint
- bugfix/health-response
- docs/pr-template
- docs/contributing-rules

## 3. Правила коммитов

Формат: <тип>: <описание изменения>.

Используем Conventional Commits:
- feat — новая функция;
- fix — исправление ошибки;
- docs — документация;
- style — форматирование;
- refactor — рефакторинг;
- test — тесты;
- chore — технические задачи;
- merge — разрешение конфликтов при объединении веток.

Примеры из истории нашего репозитория:
- 17585f3 — feat: add initial FastAPI application with health check
- 2986379 — docs: initial project structure and contributing guidelines

## 4. Регламент code review

Автор PR назначает другого участника команды ревьюером.
Первый ответ ревьюера — в течение 24 часов.

Автор отвечает на каждое замечание: вносит исправление
или объясняет свою позицию.
Завершённое обсуждение закрывает оставивший его ревьюер.

После доработки автор запрашивает повторную проверку.
Для объединения требуется минимум один approval
от другого участника с правом записи в репозиторий.
Собственный PR участник не одобряет.

Если за два круга ревью договориться не удалось,
обсуждаем вопрос на встрече команды.

## 5. Критерии approval

Ревьюер проверяет:

1. PR направлен в main, название ветки соответствует разделу 2.
2. Коммиты оформлены по разделу 3.
3. Описание объясняет задачу, изменения и способ проверки.
4. Автор заполнил чек-лист; для неприменимых пунктов указал причину.
5. В diff нет секретов, .env, .venv и посторонних файлов.
6. Имена в коде понятны, оформление единообразно,
   лишний отладочный код отсутствует.
7. Изменения размещены по назначению, логика не дублируется.
8. Проверено наличие тестов для изменённого поведения.
   Если автоматических тестов нет, автор явно указал это
   и описал ручную проверку.
9. Проверка по инструкции автора даёт заявленный результат.
   При изменении кода GET / и GET /health продолжают работать.
10. Документация соответствует изменённому поведению.
11. Автор ответил на замечания, необходимые правки внесены,
    завершённые обсуждения закрыты.

Для изменений только документации проверки кода отмечаются
как неприменимые с объяснением причины.

Если применимый критерий не выполнен, ревьюер выбирает
Request changes и указывает номер пункта и необходимую правку.
Если все применимые критерии выполнены — Approve.

## 6. Разрешение конфликтов в коде

Находясь в своей рабочей ветке, получить актуальную main:

```bash
git fetch origin
git merge origin/main
``` 

Открыть файлы, отмеченные Git как конфликтующие.
Согласовать итоговое содержимое, удалить маркеры
<<<<<<<, ======= и >>>>>>>.

Проверить результат, затем выполнить:

```bash
git add <путь-к-исправленному-файлу>
git commit -m "merge: resolve conflict with main"
git push
```

В git add подставить реальные пути всех исправленных файлов.
После отправки запросить повторное ревью.
Force-push для разрешения конфликтов не используем.

## 7. Защита ветки

Защищённая ветка: main.

ЗАПОЛНИТЬ: название правила и механизм защиты
(Ruleset или классический Branch protection).

ЗАПОЛНИТЬ: фактически включённые настройки из GitHub:
- активность правила и целевая ветка;
- обязательность PR и количество approvals;
- сброс approvals после новых коммитов;
- требование закрывать обсуждения;
- запреты force-push и удаления;
- возможность обхода защиты администратором;
- дополнительные правила, если они включены.
